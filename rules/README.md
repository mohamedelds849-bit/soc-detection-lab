## Validate syntax

**Wazuh XML** (well-formedness):
```bash
xmllint --noout wazuh/local_rules.xml
```

**On the Wazuh manager** (semantic test against real log lines):
```bash
sudo cp wazuh/local_rules.xml /var/ossec/etc/rules/local_rules.xml
sudo systemctl restart wazuh-manager
sudo /var/ossec/bin/wazuh-logtest     # paste a log line, see which rule matches
```
Windows (eventchannel JSON) lines do not reach the Windows rules in
`wazuh-logtest` on a stock manager (rule 60000 requires `decoded_as
windows_eventchannel`); see WAZUH-VALIDATION.md §0 for the temporary workaround
used by Wazuh's own ruleset tests.

**Sigma YAML** (spec validation + conversion, verified with sigma-cli 3.1 / pySigma 1.5):
```bash
python -m pip install sigma-cli
sigma check sigma/                          # -> 0 errors, 0 condition errors, 0 issues
sigma plugin install splunk
sigma convert -t splunk --without-pipeline sigma/rdp_bruteforce.yml
```
Several files contain more than one YAML document (a base rule plus a Sigma v2
**correlation rule** that references it by `name`). Two correlations are
**chained** on another correlation: `success_after_failures.yml` uses the
`event_count` rule of `ssh_bruteforce.yml`, and `rdp_success_after_bruteforce.yml`
uses `lab_win_failed_logon_burst` from `rdp_bruteforce.yml`, so check/convert the
whole directory. There is no official pySigma backend for Wazuh, which is why the
Wazuh rules are hand-written. The Splunk backend does not support
`temporal_ordered` correlations.

## Wazuh design notes (read from the v4.9.2 source, not yet confirmed live)

- **Sibling order.** Children of a rule are evaluated by descending level, then in
  load order (`src/analysisd/rules_list.c`, `_OS_AddRule`). Built-in rules load
  before `local_rules.xml`, so a built-in sibling with the same level wins. The
  built-in brute-force rules 5763 (SSH) and 60204 (Windows) use the same
  threshold as the lab (8 events), so the custom counters are attached as their
  **children** instead of competing with them. The success-after-brute-force
  rules use level 13 so they are tried before the built-in 40112 (level 12).
- **frequency.** `frequency="8"` fires on the 8th matching event (the loader
  subtracts 2, see `rules.c`; confirmed by the 8-line `sshd.ini` test for 5763).
- **Correlation scope and time.** Per agent by default; the time window is the
  manager's reception time, not the event timestamp.
- **Known differences** with the engine/Sigma versions are listed in
  WAZUH-VALIDATION.md §3 (60204 uses 240 s; 100131 cannot join on the SID; the
  port-scan rule counts connections, not distinct ports).
- Wazuh's default regex engine (OSRegex) does not understand `(?i)` and similar
  PCRE syntax, so those fields declare `type="pcre2"`.
- ATT&CK: Sigma/engine use ATT&CK v19 IDs (T1685, T1685.005); the Wazuh rules keep
  T1562.001 / T1070.001 because Wazuh's bundled MITRE database predates v19.
